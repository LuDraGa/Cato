## Release Build Defines

Use `.env` and `make build-production` so secrets and release URLs do not live in source:

```bash
cp .env.example .env
# Fill in SENTRY_DSN and PRIVACY_POLICY_URL.
make build-production
```

`tools/build_production_appbundle.sh` always emits split debug information to
`build/sentry-debug-info` unless `SPLIT_DEBUG_INFO_DIR` is overridden.

## GitHub Actions

The repo has two release-support workflows:

- `ci.yml` runs formatting, analyze, and tests on PRs and `main`. On `main`
  pushes and manual dispatches, it also builds a release AAB artifact.
- `sync-privacy-policy.yml` updates the public Privacy Policy Gist when
  `docs/privacy-policy.md` changes on `main`.

Required repository secrets:

| Secret | Purpose |
|---|---|
| `SENTRY_DSN` | Enables Sentry in CI release builds |
| `SENTRY_AUTH_TOKEN` | Lets `sentry_dart_plugin` upload debug files/source context |
| `PRIVACY_POLICY_URL` | Injects the Play-visible privacy policy URL into the app |
| `GIST_TOKEN` | Lets GitHub Actions patch the Privacy Policy Gist |
 
The privacy policy Gist is
`https://gist.github.com/LuDraGa/a934812433d827796414ee475d189628`.

The first Sentry CI integration uploads debug files/source context only. Sentry's
GitHub app can be connected later for issue linking and commit association.

## Firebase Decision

For v0.1.0, Firebase is not required for release. Current Firebase Core initialization is optional and only runs when build-time Firebase values are supplied.

Defer Firebase setup until accounts, login, cloud backup, or partner sharing is being implemented. When that happens, decide the Firebase products deliberately:

- Firebase Auth for accounts.
- Firestore for sync/sharing data.
- Cloud Functions only if server-side enforcement or fanout is needed.
- Firebase Analytics only if you are ready to disclose analytics collection in Data safety.

Do not add Firebase products just for v0.1.0 Play submission.

## Sentry Production Posture

Current app posture:

- Sentry is disabled unless `SENTRY_DSN` is supplied.
- Environment defaults to `production` in release builds.
- `sendDefaultPii=false`.
- Screenshots and view hierarchy attachments are disabled.
- Performance tracing is disabled with `tracesSampleRate=0.0`.
- User interaction tracing is disabled.

Before Play upload:

- Create a Sentry project for Cato Android.
- Build a local release or internal test build with a non-production environment first.
- Trigger a test error and inspect the event payload.
- Confirm no tracker entry values, notes, photos, screenshots, or view hierarchy are attached.
- Add Sentry crash/diagnostic collection to Data safety and Privacy Policy.

## Shorebird Workflow

Shorebird is useful after the first Play release, but it does not replace Play's first app submission, signing, Data safety, or review process.

Current local status:

- Shorebird CLI is installed at `/Users/abhiroopprasad/.shorebird/bin/shorebird`.
- `shorebird doctor` passes URL reachability and Android INTERNET permission checks.
- Remaining setup requires `shorebird login` and `shorebird init` so Shorebird can create a real `shorebird.yaml` with an app id.

Recommended sequence:

1. Log in: `/Users/abhiroopprasad/.shorebird/bin/shorebird login`.
2. Initialize from the repo root: `/Users/abhiroopprasad/.shorebird/bin/shorebird init --display-name "Cato"`.
3. Commit `shorebird.yaml` and the `pubspec.yaml` asset entry generated by Shorebird.
4. Complete Play signing and upload the first `.aab`.
5. Once the Play release is live on a testing track, create Shorebird releases from the same version/build.
6. Use Shorebird only for small Dart-side fixes that comply with Play policies.
7. Do not use Shorebird to introduce undisclosed data collection, account flows, policy-sensitive changes, native permission changes, or store-listing mismatches.

Suggested docs command flow after Shorebird is configured:

```bash
shorebird release android --artifact appbundle
shorebird patch android
```

## Android Version and Device Scope

The app now sets `minSdk=26`, limiting installs to Android 8.0+.

Rationale:

- Reduces old Android behavior and permission edge cases for the first release.
- Keeps support broad enough for meaningful closed testing.
- Works with the current local-first MVP scope.

The manifest marks camera hardware as not required so devices without a camera are not accidentally excluded only because the app can request camera permission. Device-specific exclusions should be handled in Play Console Device catalog after closed testing reveals concrete failures.
